# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The Dailies: a friends leaderboard for daily web games (Wordle, Connections, NYT Mini, LinkedIn games, Worldle, GeoGuessr, etc.). Users paste a game's share text; a hardcoded regex parser identifies the game, extracts the score, and checks it is today's puzzle. No AI or external APIs are involved.

## Commands

```bash
npm install && npm --prefix web install   # two separate package trees: root (API) and web/ (Vite + React)
npm run dev        # API on :3001 (node --watch) + Vite on :5173; Vite proxies /api to :3001
npm run build      # installs web deps and builds the frontend into web/dist
npm start          # production: the Express server serves web/dist and the API on one port
```

There is no linter or TypeScript. `npm test` (`node --test server/parsers.test.mjs`) checks that every real share in `apple/capture/fixtures/<gameId>.txt` is detected as that game; add a fixture only from an actual share. To check a parser against a sample share string:

```bash
node --input-type=module -e "import {detect} from './server/parsers.js'; console.log(detect(\`Wordle 1,234 3/6\`))"
```

Native app (`apple/`, see `docs/native-app-plan.md`), XcodeGen-generated (the `.xcodeproj` is gitignored):

```bash
cd apple && xcodegen generate     # export DAILIES_TEAM=<team id> first to sign; never commit a team id
                                  # DAILIES_PUSH=-Push signs with push notifications (paid team only)
xcodebuild -project apple/Dailies.xcodeproj -scheme Dailies -destination 'platform=iOS Simulator,name=iPhone 17' -derivedDataPath apple/build/DerivedData build
```

UI tests (`apple/DailiesUITests`, scheme `DailiesUITests`) drive the gestures that can't be checked by hand in the Simulator: swiping days on the crown card, the + Add score tab and press-and-drag reordering. They need `npm run dev` and a Simulator signed in on the local server: `xcodebuild test -project apple/Dailies.xcodeproj -scheme DailiesUITests -destination '<simulator>' -derivedDataPath apple/build/DerivedData`.

Debug builds accept launch arguments for scripted Simulator runs: `-dailiesServer local`, `-dailiesEval "<js>"` (runs once after the first page load), `-dailiesTestWordle YES`, for the in-app game browser `-dailiesOpenGame <url>` and `-dailiesGameEval "<js>"`, `-dailiesScreenshots YES` (hides the debug gear for App Store screenshots), and `-dailiesTab feed|friends|you` / `-dailiesGame <gameId>` / `-dailiesAddSheet YES` to open a native screen, `-dailiesSignIn "<user> <password>"` to sign in a local test account (local server only) (full list in `apple/Dailies/DebugMenu.swift`). On the Mac use `/usr/bin/log`, because zsh has a `log` builtin. Logs: `xcrun simctl spawn booted log show --info --predicate 'subsystem == "lol.thedailies"'`.

## Architecture

**Backend (`server/`, Express, ESM, plain SQL):**
- `db.js`: if `DATABASE_URL` is set it uses `pg` (Railway Postgres), otherwise embedded PGlite stored in `./data/pg` (gitignored, so local dev needs no setup). Both sit behind the same `q(text, params)` helper, so SQL must work on both. `schema.sql` runs on every boot with `CREATE ... IF NOT EXISTS`. There is no migration system, so changing an existing table needs a manual plan.
- `auth.js`: bcrypt + JWT in an httpOnly cookie (`db_token`). `requireAuth` (async) also accepts `Authorization: Bearer dly_...` device tokens from the `api_tokens` table (sha256-hashed, max 10 per user, managed at `/api/auth/tokens`) and checks them before the cookie. It sets `req.user = { id, username }`. The `JWT_SECRET` env var is required in production.
- `friends.js`: `friendships` stores one row per pair, normalized so `user_a < user_b` (use the `pair()` helper). `circleIds(userId)` (self + accepted friends) defines who appears on a user's board and feed. `/api/friends/suggestions` is "People you may know": friends of friends through accepted friendships only (a pending request reveals nothing), most mutual friends first, minus anyone with a friendship row either way and anyone closed (`friend_suggestion_dismissals`); `?via=<friend id>` keeps to one friend's friends, shown on Friends right after adding them.
- `submissions.js`: `POST /api/submissions` accepts either `{ text }` (parsed and verified) or `{ gameId, value }` (manual entry, allowed only when `game.manual`, stored with `verified=false`). Each user gets one submission per game per `puzzle_date` (enforced by a DB unique constraint and checked before insert, returning 409).
- `points.js`: every score is worth 0–100 from the result alone: `perfect` scores 100, `par` (a typical result for the game itself) 50 and `zero` or worse 0, on a t^1.5 curve each side of par. The defaults are `SCORING` in `parsers.js`; admins override them in the `game_scoring` table. Points are saved on the submission (`submissions.points`) when it's posted, so changing a game's values only affects new scores (rows missing points are filled in at boot).
- `scoring.js`: `buildBoards(rows)` ranks each game's board by the raw result (competition ranking, 1-2-2-4). The daily "crown" is the sum of a user's saved points; a tie goes to whoever played fewer games, and a tie on both shares the rank. `/stats` adds up daily points the same way and ranks all-time per-game boards by best result, then average.
- `feed.js`: `/api/feed` is one card per player per day (Strava-style): points total, their games, a PB tag when a score beats all their earlier ones, and the streak up to that day. The highlight leads the card in yellow: the game they picked for today (`day_highlights`), or else their top-points game. Friends give a day kudos (`day_kudos`, one per giver); unseen kudos drive the badge on the Feed tab (`/api/feed/unseen`) and clear when the owner opens the feed. Pages go back `DAYS_PER_PAGE` days at a time (`?before=`).
- `push.js`: push notifications through APNs (HTTP/2 with a .p8 token key; env `APNS_KEY`, `APNS_KEY_ID`, `APNS_TEAM_ID`, optional `APNS_TOPIC`; with no key nothing is sent). The app registers devices at `/api/push/devices` (`push_devices`, removed on sign-out, account deletion, or when Apple says the token is gone). `notify(userId, {...})` never throws; kudos (`notifyKudos`, collapsed per day), friend requests and accepts, and an evening reminder at `PUSH_REMINDER_HOUR` Eastern (default 20) for anyone with a device and no score that day (`push_reminders` stops a restart sending it twice). Payloads carry `tab` for the app to open. To try it locally, `APNS_HOST` points at a stand-in server.
- `release.js`: the Mac app downloaded from the website. `GET /api/app/mac` (no sign-in) returns the newest build from `server/mac-release.json`, and `/download/mac` redirects to its .dmg on GitHub Releases. With no file, there is no download and the site offers none.
- `meta.js`: link previews. The server writes `<title>` and Open Graph tags into `index.html` for every page (at `<!-- server meta -->`; static `index: false` so `/` comes through it). An invite link (`/?add=username`, a real user) previews as "Add @username on The Dailies"; the image is `web/public/og.png`, drawn by `apple/tools/make-og-image.swift`. The tab and home-screen icons (`favicon.png`, `apple-touch-icon.png`) are the app icon.
- `admin.js`: `/api/admin` (admins only: `ADMIN_USERNAMES`, default nickpianfetti and vishruthanand) edits scoring values and marks game suggestions added or removes them. The website shows an Admin tab to admins; there's no native admin UI.
- `util.js`: all "today" logic uses **US Eastern** (`America/New_York`, `todayISO()`). Dates are passed around as ISO `YYYY-MM-DD` strings.

**Parsers (`server/parsers.js`) are the core of the app.** `GAMES` is the single registry: the frontend gets tile metadata from `GET /api/submissions/games`, and boards, feed, and scoring all key off `game.id`. Each entry has:
- `parse(text)`: returns `{ puzzleNumber?, date?, metric, display }`, or `null` if the text isn't this game.
- `better`: `'lower' | 'higher'`, which sets the sort direction for `metric`.
- `epoch: { date, first }`: the date of puzzle `#first`, used to derive the puzzle's date from its number. If it is `null`, the date can only come from text embedded in the share.
- `dateTolerance`: the number of days the derived date may differ from today. If no date can be derived, the staleness check is skipped.
- `manual`: also accept a typed-in score.
- `paid`: `{ what, deals: [{ label, url|null }] }` for games behind a subscription (currently only The Mini). The tile shows a `$` badge that lists the deals.
- `scoring` (from the `SCORING` map below `GAMES`): `{ perfect, par, zero, failAt? }` in the game's metric (times in seconds). Every game needs one.
- `category`: one of `CATEGORIES` (NYT Games, LinkedIn, Geography, Words & Trivia). Today groups games by it (players collapse and reorder groups; saved in `user_prefs.category_order`/`collapsed`), and `buildBoards` returns a crown per category (`categoryCrowns`). `/stats` returns per-category standings too.
- `embed`: the site allows being framed, so Play on the website opens it in `GamePanel.jsx` (iframe plus a clipboard Paste button). Only games verified to render in an iframe get this; NYT, LinkedIn, Krillion, EthnoGuessr and GeoGuessr refuse framing, and Worldle/Travle ask not to be framed.

`detect()` tries each game **in array order** and returns the first non-null result, with exceptions swallowed per game. A new or loosened regex can therefore steal another game's share text, so put specific patterns before general ones. LinkedIn games share a single `linkedinGame()` factory. Their epoch dates are best-effort, which is why they have `dateTolerance: 3`. Failed puzzles are mapped to a worse-than-max metric (e.g. Wordle `X` → 7, failed Connections → 5).

Adding a game = adding one `GAMES` entry. No frontend change is needed.

**Frontend (`web/src/`, React 18 + Vite, no router or state library):** On Today, a game you've played shows "Next in 4h 12m" (to local midnight, when most games put out the next puzzle) in place of Play, and the board reloads itself at midnight. Scores go in through a floating Paste button at the bottom right (`PasteDock.jsx`): one click reads the clipboard and saves; where the browser won't share it, a small box opens to paste into, and ⌘V / Ctrl+V anywhere on Today saves too. `App.jsx` switches between the tabs `today`, `feed`, `friends`, and `you` (`Profile.jsx`: my stats, password, devices) using local state. The per-user home layout (game order and favorites) lives in `user_prefs` (`/api/prefs`). `DELETE /api/auth/account` (password-confirmed, from the You tab) removes a user and every row that references them. App Store review requires it, so any new table with a `user_id` must be added there. `web/public/privacy.html` and `support.html` are served at `/privacy` and `/support`; they are the App Store listing's URLs, so keep the privacy policy in step with what the app stores. `Leaderboards.jsx` (on Friends) and `Profile.jsx` both read `/api/submissions/stats`, which re-runs `buildBoards` per day for my circle. Game suggestions are in `/api/suggestions`. `api.js` wraps `fetch('/api' + path)` and throws `Error(data.error)` on non-2xx responses. Server error messages are written to be shown to users directly. Invite links (`/?add=username`) are held in `App` across login and consumed by `Friends.jsx`, which sends the request. `native.js` is the bridge to the iOS/macOS shell. It is inert in normal browsers. In the app (user agent contains `TheDailiesApp/`) it reports the session, issues a device token on request, and routes Play through native.

**Native app (`apple/`):** on iPhone, a native SwiftUI UI (`Dailies/Native/`, being built in stages): `AppSession` holds sign-in (native login mints a device token and hands the site cookie to the web view), `AppTabs` is the tab bar, Today is native (`TodayModel`/`TodayView`/`GameDetailView`) and so is Feed (`FeedModel`/`FeedView`, which also polls `/api/feed/unseen` for the tab badge). Friends and You still show the site in the shared web view with its header and tabs hidden by an injected style. Colors are light/dark tokens in `Assets.xcassets` (`Theme.swift`). Use Dynamic Type styles and SF Symbols, not fixed sizes or emoji icons. Tappable things press in: chunky buttons sink into their offset shadow on hover/press (`.pressIn(...)` ButtonStyle in the app, the press-in block in `styles.css` on the site). Tapping anywhere on a game plays it; its board is behind the ⓘ button. Text never wraps: use `.oneLine()` (one line, overflow hidden with a fade), except error messages. The palette is lavender and yellow only (no coral in the app); buttons and links use ink. The Mac app's window is the website itself, its sign-in page, header and tabs included (signing in there mints the device token through the `session`/`token` bridge, and `AppSession.webSignedIn` records it; the native Today, Feed, sign-in and Add Score screens are iPhone-only) (`MacRootView` hosts the shared web view; the iPhone hides the site's header, the Mac doesn't), so it looks just like the site. Native around it: the menus (`DailiesCommands`: Go › Previous/Next Day and Today ⌘[ ⌘] ⌘T fire `dailies:day` in `Today.jsx`, ⌘1–4 switch the site's tabs, File › Add Score… ⌘N fires `dailies:pastebox`, Edit › Paste Result ⌘⇧V fires `dailies:paste`), the site's Paste button reading `NSPasteboard` through the `dailiesClipboard` reply handler (no WebKit paste prompt; the app sets `window.__dailiesNative` at document start), notifications, the game panel, updates, and a "Can't reach The Dailies" card (`CantReach`) when the site doesn't load, which retries by itself once the Mac is back online. Play on the Mac opens `GamePanel.swift`, the website's game panel drawn natively over the page (the site's tokens are in `Site`): every game loads there, since the app's web view isn't an iframe, and Window ↗ pops it out to its own full-screen window (`GameBrowserView`). Native submissions never go through the web view. They use `DailiesAPI` (`URLSession` + bearer token from the shared keychain) via `SubmissionQueue`. The iOS share extension (`DailiesShare/`) posts directly with the same token. Play on any game site in `GameHosts.all`, the server's game list (`learn`, from the native Today) or a game the site's own Play sent (`trust`, which is how the Mac learns new games) opens the in-app game browser (`GameBrowser.swift`, all builds). It never injects scripts into game pages. Every game works the same way: the player taps the game's own Share or Copy, then the system `PasteButton` in the bottom bar enqueues the clipboard text (no paste prompt). This matches the website's `GamePanel.jsx` flow, and keeps the app clear of modifying NYT/LinkedIn pages. Push (`Push.swift`): after sign-in the app asks for notification permission, sends its device token to the server (`sandbox` env in Debug builds), opens the tab a tapped notification names, and clears the icon badge when the Feed loads. Create web views in `onAppear`, not in a SwiftUI view's init, because SwiftUI may build views more than once. The app icon is drawn by `apple/tools/make-icon.swift`. `PrivacyInfo.xcprivacy` (app and extension) declares UserDefaults use and collected data; keep it matching the privacy policy. `appstore/README.md` has the listing copy, privacy answers and review notes.

## Mac download (outside the App Store)

Two Mac builds come from the same code. **Dailies** is the App Store (and iPhone) target: no updater, since the Mac App Store doesn't allow one. **DailiesDirect** is the website download: the same sources plus Sparkle (`DIRECT_DOWNLOAD` in Swift, its own Info.plist `Config/DailiesDirect-Info.plist` with the feed and public key, Sparkle's XPC mach-lookup entitlements, and its own build folder so the App Store build never picks up `Sparkle.framework`). Sparkle reads `thedailies.lol/appcast.xml` (`server/release.js`, built from `server/mac-release.json`) every 6 hours, downloads a newer build in the background and installs it when the app quits; App menu › Check for Updates… asks right away (`MacUpdates.swift`). Copies from before Sparkle (builds 1–4) still use `/api/app/mac` and the update card, so they reach a Sparkle build once by hand.

`DAILIES_TEAM=<team id> apple/tools/release-mac.sh "What's new" [--publish]` archives DailiesDirect, signs it with Developer ID, notarizes it (notarytool profile `dailies-notary`), staples it and builds `apple/build/release/TheDailies-<version>-<build>.dmg` (`make-dmg.sh`: the themed drag-to-Applications window drawn by `make-dmg-background.swift`), which is notarized too, then signs the `.dmg` for Sparkle with the EdDSA private key in this Mac's keychain (made once with Sparkle's `generate_keys`; back it up with `generate_keys -x <file>`: installed copies only accept updates signed with it). `--publish` uploads it to a GitHub release (`mac-<version>-<build>`) and writes `server/mac-release.json` (with the signature and size); commit that and deploy. Bump `CURRENT_PROJECT_VERSION` first: only a higher build is offered. To try an update locally, run a Debug DailiesDirect build with `-dailiesFeedURL <feed>`. The website offers the download to Mac browsers once as a popup and always on the You tab (`MacApp.jsx`).

## Deploy

Railway (Nixpacks): `npm install` → `npm run build` → `npm start`. A Postgres service provides `DATABASE_URL`, and `JWT_SECRET` must be set on the app service.
